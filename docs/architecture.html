From one prompt to a trained model — end to end

01 The seven decisions

Everything downstream is a consequence of these. They exist because the current system is a single tabular-CSV path with a global state blob, and neither survives contact with computer vision or a rented GPU.

D1

Modality routes the pipeline

Extraction declares tabular / text / vision / audio / timeseries. Each gets its own preprocessing tools and trainer recipe, sharing one contract on both ends.

D2

Typed per-run contract

A runs/<id>/ directory of small validated documents replaces pipeline_state.json — killing the overloaded status key and enabling concurrent runs.

D3

Research is a tool, not a phase

An AgentTool any agent can call mid-task, disk-cached. The pre-phase researcher couldn't answer questions that only arise later.

D4

Generated code passes a gate

Doc grounding, then ruff and AST checks, then a sampled smoke run — before any full training run is paid for.

D5

Leakage enforced by a linter

Instructions already failed at this: imputation still fits on the full dataset today. An AST pass asserts fit-after-split instead of asking for it.

D6

Hardware profile is a budget

A scan that only informs the prompt gets ignored. The derived budget is enforced — the gate rejects scripts that exceed VRAM, batch, or time.

D7

Execution is a swappable backend

Local Docker, local venv, JarvisLabs, RunPod, Colab behind one interface. A deterministic broker picks — never the LLM.

D7a

Money and data have guardrails

Every remote instance runs on a lease with a TTL supervisor that terminates regardless of agent state. Data egress is per-run opt-in.

02 The full run, start to end

Seven stages. Each writes one typed document, and the next stage reads only that — so a crash resumes from disk and a phase can be re-run in isolation.

03 Modality routing

Today datasets/ is scanned for CSVs and everything downstream assumes a DataFrame — which is why the NLP path is broken end to end: HuggingFace datasets are saved as Arrow shards that the scanner cannot read.

04 Making generated code trustworthy

Your ask was that agent-written code behave like a careful human's — reading current docs, following best practice, checking when unsure. That becomes four mechanical steps, because prompt instructions demonstrably do not hold.

Why leakage needs a linter, not an instruction

The current system correctly defers scaling and target encoding out of preprocessing — but imputation, frequency encoding, and outlier bounds are still fit on the full dataset, and the existing validator cannot detect that. Every metric it reports is optimistic by an unknown margin.

05 Compute: local first, rented when it earns it

You want data and processing local. Rented GPUs contradict that for whatever gets uploaded — so remote is a deliberate, per-run choice with the boundary drawn explicitly, never a silent fallback.

Why a lease, and not a stop button

The existing stop_colab_runtime() can only write a script asking the model to release the GPU. Rented instances bill by the minute, so teardown cannot be an agent decision.

06 What a run leaves on disk

Your definition of done, made checkable. verify_bundle() fails the run when anything here is missing, so "complete" is asserted rather than hoped for.

07 Build order

Sequenced by dependency. M0 first because deep learning on top of untrustworthy metrics multiplies the debugging surface without adding anything.

MilestoneScopeDone whenEst.
M0 Correctness & hygiene — leakage, reproducibility, sandbox hardening, first tests Two runs on the same CSV are byte-identical; every fixed bug has a test 1 wk
M1 Package, run contract, CLI, doctor pip install -e . → accurate readiness table on a clean Windows box 2 wk
M2 Research as a tool + slot-gated adaptive interview Two different ideas produce visibly different question sequences 1 wk
M3 Codegen quality gate A deliberately leaky script is rejected before execution 1.5 wk
M4 Text/NLP pipeline — fixes the broken HuggingFace path "Classify support tickets by urgency" trains unattended 2 wk
M5 Compute backends — local GPU, JarvisLabs, RunPod, leases Same job runs unmodified on all three; SIGINT kills the remote instance 2 wk
M6 Vision pipeline + deep-learning trainer Image classification end to end; degrades gracefully to CPU 2.5 wk
M7 Deliverable bundle & polish verify_bundle() green on every supported modality 1 wk

M5 sits before M6 deliberately: vision is what actually needs the GPU, and debugging a new pipeline and a new execution backend at the same time means never knowing which one broke. The backends land against the already-working text trainer first.

08 Open before I start

Six calls that change what gets built. My recommendation is marked on each — say "go" and I'll take these as answered.

  1. Cost ceiling default Should --max-cost-usd default to something non-zero so an unattended run can never surprise you? Recommend $5 default, override to raise.
  2. Disposition when a run finishes PAUSE keeps the instance warm but storage still bills; DESTROY costs nothing and restarts cold. Recommend DESTROY by default, --keep-warm to opt in.
  3. Colab's future JarvisLabs and RunPod are strictly better behaved — real APIs, real teardown. Recommend demoting Colab to "supported if configured, never auto-selected".
  4. Host-venv consent It's the only path that drops isolation entirely. Recommend per-run confirmation rather than a global opt-in at setup.
  5. Vision dataset ceiling Cap by rows, gigabytes, or wall-clock — and is subsampling automatic or does it prompt you? Recommend GB cap with a prompt, since transfer cost dominates.
  6. Model registry Do repeated runs on the same dataset accumulate a comparable history, or is each run standalone? Recommend standalone for now — revisit after M7.
